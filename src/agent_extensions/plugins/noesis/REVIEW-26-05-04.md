# Noesis Plugin — End-to-End Flow Analysis

> Goal: support an AI-native SDLC for complex IT systems. Capture intent (conversations, design drafts) → curate knowledge (topics, decisions) → design (Design Doc as a diff) → implement (real code, sealed against the diff) → iterate.

This document maps the actual flows users go through, the friction they hit, and a set of e2e scenarios that must hold. It then proposes concrete improvements ordered by impact.

---

## 1. Recap of moving parts

### 1.1 Skills

| Skill | Reads | Writes (`<projectDir>/noesis/`) | Touches user code |
|---|---|---|---|
| `analyze-conversation` | transcript md | `conversations/{id}.{md,json}`, `topics/`, `decisions/` | no |
| `analyze-design-draft` | document md | `documents/{id}.{md,json}`, `topics/`, `decisions/`, optionally `design-docs/` | no |
| `create-design-doc` | graph + user files | `design-docs/{slug}-{id}.json` | no |
| `implement-design-doc` | a saved design doc | sets `implemented=true` on the doc | **yes — generates/edits C# source** |
| `search-topics` | graph | — | no |

### 1.2 Persistence model

- **Source of truth** = files under `<projectDir>/noesis/`. Graph DB is a cache rebuilt by the indexer on boot + filesystem-watch.
- Every json file carries `edited_by_user: boolean`. Splitter writes `false`; loader flips to `true` when it detects on-disk drift it didn't drive. When `true`, the splitter **skips the file** on the next merge (user wins).
- Cross-references store `source_sha`. When the source file changes, dependents (topics/decisions) are flagged `is_stale`.
- All write MCP tools are wrapped by `gateWriteTool`: while the indexer is `indexing` or `error`, writes return `{ status: "NotReady" }`.

### 1.3 Sealed Design Doc

- After `implement-design-doc` runs verification (`compare_implementation_to_design`), it calls `mark_design_doc_implemented`, setting `implemented=true`.
- Sealed doc → `save_design_doc` rejects with 409, UI shows error. The only forward path is **a new design doc**.

### 1.4 UI write surface (current)

PATCH `/api/ui/topics/:id` (title, summaries) · PATCH `/api/ui/decisions/:id` (+ alternatives) · PATCH `/api/ui/design-docs/:id/elements` · PUT `/api/ui/actors/:name` · POST `/api/scan`. **No DELETE endpoints.** **No flag-reset endpoint.** **No git/branch awareness.**

## 2. End-to-end test scenarios

Numbering matches sections below. Each scenario is one end-to-end happy-or-strange path through the plugin. Bold marks the **invariants** the system must preserve.

### 2.1 Canonical happy path (greenfield)

1. Empty project. Run `analyze-conversation` on a transcript.
   - **Invariant**: `conversations/{id}.{md,json}` written; topics/decisions populated; index becomes `consistent`.
2. Run `analyze-design-draft` on a design memo referring to the same topics.
   - **Invariant**: existing topics are *reused* (Goldilocks), not duplicated; `documents/` populated; if a model is detected, `design-docs/` is created.
3. Run `create-design-doc` — pulls graph + user files, produces a diff design doc (added/modified/removed).
   - **Invariant**: scratch files in `working_dir`, canonical JSON only via `save_design_doc`.
4. Run `implement-design-doc`.
   - **Invariant**: scanner before/after diff matches the design doc's ChangeSet exactly; `implemented=true` set; on disk both `noesis/design-docs/...` and the C# source tree are committable as one logical change.

### 2.2 Iteration on an unsealed doc

5. After (3), user spots a missing rule. Re-run `create-design-doc` with the same `design_doc_id` → `save_design_doc` overwrites JSON.
   - **Invariant**: `edited_by_user` reset to `false`; UI editor stays open; topics/decisions unaffected.

### 2.3 Iteration after sealing

6. After (4), user wants v2. Run `create-design-doc` for a *new* doc that references the implemented one.
   - **Invariant**: new diff is computed *against the current implemented baseline*, not against an empty repo.
   - **(Currently fragile — see §3.4.)**

### 2.4 Strange / out-of-order skill invocations

7. `create-design-doc` on an empty graph (no conversations, no documents) → must succeed using only the user-supplied files.
8. `analyze-conversation` *after* a design doc is sealed — captures new ideas without touching code.
9. Two `analyze-conversation` runs on the same transcript → idempotent (content-addressed id).
10. `analyze-design-draft` on a document that's already been merged → idempotent; skipped if `edited_by_user` is on.
11. `implement-design-doc` invoked twice for the same doc → second call sees `implemented=true` and bails out clean (no destructive re-implement).
12. User skips `analyze-*` entirely and goes straight to `create-design-doc` with file paths only.
13. `analyze-conversation` referencing topics already locked by the user (UI edits) → splitter skips the locked topic; new items are dropped or routed to a new sibling (must be deterministic, not lost).

### 2.5 Git operations

14. **Branch switch**: user switches from `feat/A` to `feat/B`. `noesis/` differs significantly. Indexer must full-rescan; stale `SourceFile` rows must be reconciled; `implemented` flags reflect branch B's state.
15. **`git pull` with merge of `noesis/*.json`**: conflict markers may end up in JSON files → indexer must surface this as `state="error"` with a clear message (currently it might just throw on JSON parse).
16. **`git reset --hard`** removes a design doc → indexer detects vanished files, removes graph node.
17. **Stash/pop** of `noesis/` files → flurry of FS events; debounce holds; final state consistent.
18. **Worktree / submodule** users — `<projectDir>` may be a worktree path that differs from `cwd`. Indexer must use the right root.

### 2.6 Manual UI edits

19. User edits a topic summary in UI → file saved with `edited_by_user=true` → next `analyze-conversation` skips that topic file but still records new idea_units against it (or routes to a sibling).
20. User edits a decision text in UI; later the source conversation is re-merged → `is_stale` shown; user must explicitly re-sync.
21. User edits an element in a sealed design doc → 409 → UI shows actionable banner ("create iteration v2").
22. User edits an element in an unsealed design doc → next `create-design-doc` run sees `edited_by_user=true` and refuses to overwrite without confirmation.

### 2.7 Manual code edits after `implement-design-doc`

23. User refactors C# manually after sealing. The next `create-design-doc` (v2) is invoked.
   - **Expected**: the new diff is computed against *current code* (scanner output), not against the v1 design doc. Any drift the user introduced becomes part of v2's "modified" / "added" entries.
24. User deletes a Building Block project from disk after sealing. `compare_implementation_to_design` is *not* re-run (it only ran during implement). Drift is invisible until v2.

### 2.8 Failure / recovery

25. `merge_conversation` invoked while indexer is mid-scan → `NotReady` returned; agent retries after the indexer settles.
26. Splitter writes half a topic file then crashes → next boot scan sees a malformed JSON → indexer enters `error` state, identifies the offending file, exposes it via `/api/health/index`.
27. Two skills running concurrently both attempt `save_design_doc` on the same id → second call must serialize cleanly (currently no per-file lock — last write wins on disk).

## 3. Problems found in the current implementation

Each problem is anchored to a scenario above.

### 3.1 No git awareness anywhere (scenarios 14–18)

**Problem.** The indexer watches `<projectDir>/noesis/` only. It has no notion of HEAD changes, no debounce after `git checkout`, and JSON files containing merge-conflict markers will throw inside the loader. Branch hygiene is fragile.

**Effect.**
- After a branch switch, ten of files change at once → the watcher fires N debounced reindex passes. During the storm, every write tool returns `NotReady`.
- A `noesis/*.json` merge conflict crashes the loader; the user sees `state="error"` with an opaque parse trace.
- An "implemented" design doc on branch A appears as "implemented" on branch B even if branch B never built that code.

### 3.2 Sealed-doc dead-end (scenarios 6, 21, 23)

**Problem.** Once `implemented=true`, the doc is read-only forever. If the user later realises a rule was wrong, or the implementation drifted, there is no way to:
- annotate the sealed doc with a correction;
- amend a small mistake (e.g. typo in a name) without producing a fresh full-sized v2;
- detect that hand-edited code has drifted from the sealed contract (no continuous comparator).

**Effect.** Users either (a) bypass the system and edit the JSON directly (silently flipping `edited_by_user=true`), or (b) generate sprawling "v2" docs whose sole purpose is fixing one typo.

### 3.3 No deletes from the UI (multiple scenarios)

**Problem.** The UI cannot delete a conversation, document, topic, decision, design doc, BC, Module, BB, Rule, Scenario, Actor, or alternative-option. `delete_design_doc` exists as MCP tool only.

**Effect.** Cleanup forces the user to `rm` files by hand → the loader flips `edited_by_user` on whatever's left and the user loses the ability to re-merge. Garbage accumulates.

### 3.4 No "implementation baseline" decoupled from the sealed doc (scenario 23)

**Problem.** `create-design-doc` is documented as "produces a diff against currently-implemented code", but the code's "current state" is only captured in transient scanner output. There is no persistent "this is what's implemented today" record beyond the most recent sealed design doc — and that doc is the *intent*, not a snapshot of reality after manual edits.

**Effect.** Drift between intent and code is invisible. The next iteration's diff can subtract things the user already deleted by hand (no-op) or fail to surface things the user added (false-clean).

### 3.5 `edited_by_user` lock has no UI release (scenarios 19, 20, 22)

**Problem.** A single accidental UI keystroke locks a topic/decision permanently against future skill runs. The only way to release is to edit the JSON file by hand and flip the boolean — which itself flips it back to `true` on save.

**Effect.** Legitimate skill outputs silently get dropped because the file is locked. The user cannot tell unless they read `skipped_paths` in the agent's tool output.

### 3.6 No way to *create* knowledge from the UI (scenarios 19, 13)

**Problem.** UI is editor-only. There's no "new actor", "new decision", "merge these two topics", "move topic to another parent", "split a topic". All restructuring requires re-running a skill or hand-editing JSON.

**Effect.** Users can only refine what skills produce. They cannot fix structural mistakes (wrong topic parent, duplicate decisions) without leaving the tool.

### 3.7 Topic-tree edits are limited (scenarios 13, 19)

**Problem.** UI exposes title/summary edits only. `parent_id` is not editable. Items are not editable individually. Decisions inside a topic cannot be reattached to a different topic.

**Effect.** Goldilocks misclassifications are sticky.

### 3.8 No visible audit / diff of UI edits (scenarios 19–22)

**Problem.** When a user edits a topic in the UI and the splitter then skips it, the user has no way to see *what would have been written*. Tool output text mentioning `skipped_paths` is the only signal — and it's transient.

### 3.9 No conflict semantics on concurrent writes (scenario 27)

**Problem.** `save_design_doc` does not take an `If-Match: <sha>` and the splitter has no per-file lock. Two parallel agents (or one agent + UI) can clobber each other.

### 3.10 `analyze-design-draft` skip-or-save model decision is opaque

**Problem.** The skill conditionally produces a design doc based on whether the agent decides a "design model" was detected. There is no visible signal in the UI/output telling the user *why* a draft did or did not yield a design doc.

### 3.11 Indexer storm during branch switch (scenario 14)

**Problem.** Watcher debounce (250 ms) is per-file. A `git checkout` that touches 200 noesis files triggers 200 debounce timers, each scheduling a partial reindex.

**Effect.** Sustained `NotReady` for minutes; if a skill is mid-flight, it has to spin-retry through the storm.

### 3.12 No project-level health beyond indexer

**Problem.** The user has no single place to see "do my topics, decisions, design docs and code agree?" — they must inspect badges per entity.

## 4. Proposed solutions

Grouped by theme and ordered by impact-to-effort.

### 4.1 Make the indexer git-aware

- **Watch `.git/HEAD`** in addition to `noesis/`. On HEAD change, suspend the per-file watcher, run a full rescan, and only resume after `state==="consistent"`. This collapses scenario-14's storm into one reindex.
- **Detect merge-conflict markers** at the file-sync boundary: if a JSON file starts with `<<<<<<<`, surface a typed error (`state="error", reason="UnresolvedConflict", file=...`) instead of letting `JSON.parse` throw a stack trace. Let the UI render this with a "resolve and reload" affordance.
- **Stamp design docs with `implemented_at_commit: <sha>`** when sealing. UI shows "implemented on `abc1234` (current branch points to `def5678` — implementation may not match)". This restores trust across branches.
- **`<projectDir>` resolution** must follow `git rev-parse --show-toplevel`, so worktrees and submodules work.

### 4.2 Soften the seal — introduce iteration semantics

- Replace the binary `implemented` flag with a **lifecycle** field: `draft → ready → implementing → implemented → superseded`. Sealed (`implemented`) stays immutable for *content*, but a follow-up doc can declare `supersedes: <prev_id>` so the chain is browseable.
- Add a **`patch_design_doc` MCP tool** that allows a small "errata patch" against a sealed doc (rename only, no structural change). UI surfaces this as "Fix typo / rename" instead of "Create v2".
- Add a **continuous comparator**: a periodic `compare_implementation_to_design` against the most-recent sealed doc. Drift is published to `/api/health/implementation` and shown in the UI.

### 4.3 First-class manual editing in the UI

- **DELETE endpoints** for conversations, documents, topics, decisions, design docs, alternatives, actors. Each delete also cleans dependents and emits a "deleted by user" event so re-merging won't silently resurrect the entity.
- **Topic restructuring**: drag-and-drop `parent_id`, "merge into…", "split topic", "move decision to topic Y". These are pure graph ops and do not need new skills.
- **Reset-lock**: a per-entity "Release user lock" button that sets `edited_by_user=false` and stamps the registry sha to the current file sha. This is the missing pressure-release valve for §3.5.
- **Add new entities manually**: "New decision" / "New actor" / "New rule" forms — user-authored content that skills will respect (always `edited_by_user=true`).

### 4.4 Audit & feedback

- Persist **per-write audit log** under `noesis/_audit/{date}.jsonl`: `{tool, entity_id, before_sha, after_sha, by:"skill|user", at}`. UI shows "last touched by skill X" / "last touched by user".
- When the splitter **skips a file** because of `edited_by_user`, surface the diff (what *would* have been written) in a UI panel attached to that entity, with a "release lock and apply" action.

### 4.5 Concurrency & write-conflict safety

- `save_design_doc` accepts optional `if_match: <sha>` (sha of last-read JSON). Mismatch returns `Conflict` with the latest sha and a structured diff. Enforce the same for topic/decision PATCHes.
- Per-file mutex inside the splitter so parallel `merge_conversation` calls serialize cleanly.

### 4.6 Schema additions

- `Topic.locked_at`, `Decision.locked_at`, `DesignDoc.locked_at` — timestamp at which `edited_by_user` was set, so audit/UX can show "you locked this 3 days ago".
- `DesignDoc.implemented_at_commit: string`, `DesignDoc.supersedes: string|null`.
- `DesignDoc.lifecycle: "draft" | "ready" | "implementing" | "implemented" | "superseded"`.
- New entity `ImplementationSnapshot` (cached scanner output keyed by commit sha). The continuous comparator and `create-design-doc` both diff against this rather than re-scanning live.

### 4.7 New / updated skills

- **`reconcile-codebase`** (new) — given an unsealed or superseded design doc and the current codebase, generate a "this is what's actually implemented" snapshot and propose a fix-up doc. Bridges §3.4.
- **`curate-graph`** (new) — small skill driven by user requests like "merge these two topics", "split this decision into two". Operates only via graph endpoints, does no LLM extraction. Makes §4.3 callable from the agent too.
- **`analyze-conversation`** — emit `routed: { conversation_id, locked_topics: [...], reroute_targets: [...] }` so the UI/user can see *why* an item went where it went when locks were active.
- **`analyze-design-draft`** — always emit a `model_detected: boolean, reason: string` telemetry block (§3.10).

### 4.8 Health & visibility

- Extend `/api/health/index` into `/api/health/project` returning: index state, implementation drift count, locked entities count, stale dependents count, conflict-marker files. Make this the single dashboard panel on the home page.

## 5. Suggested implementation order

1. **Indexer git-awareness + conflict-marker handling** (§4.1) — small, removes the most painful surprise.
2. **Reset-lock + delete endpoints** (§4.3) — unblocks every "I made a mistake" scenario.
3. **Lifecycle field + `supersedes` chain** (§4.2) — fixes the sealed dead-end without rewriting `implement-design-doc`.
4. **Audit log + skipped-write surface** (§4.4) — turns invisible silent-skips into visible decisions.
5. **`if_match` conflict semantics** (§4.5) — required before any multi-agent or multi-user use.
6. **Topic restructuring UI + `curate-graph` skill** (§4.3, §4.7) — quality-of-life, but unlocks long-term curation.
7. **Continuous comparator + `ImplementationSnapshot`** (§4.2, §4.6) — heaviest, biggest correctness payoff.

---

## 6. What NOT to do

- Do **not** introduce a "force overwrite user edits" flag. The user-wins rule is a load-bearing safety property; any override has to be a one-shot manual reset, not a config knob.
- Do **not** put LLM reasoning inside `noesis-graph`. The CLAUDE.md rule (no Anthropic key in the MCP server) is what keeps the graph deterministic and replayable.
- Do **not** auto-run the comparator on every code edit — it's too expensive. Run it on commit/branch-switch boundaries or on explicit user request.
